The Game of Subtract-A-Square

This game is a variation on a class of Mathematical games that are related to one called Nim.

  • The game is for two players
  • Players take it in turns to play
  • The players have 3 heaps of coins.
  • Each heap will start with 13 coins.
  • They take it in turns to take coins from ONE heap.
    • The number they take must be a square - that is, 1, 4, 9….
    • They must take at least 1 coin - they can’t ‘skip’ a turn (but see below).
  • They obviously cannot take more coins than are present in a heap.
  • The player who takes the last coin wins.

Example

We will start with 3 heaps of 5 coins to keep the example short - the actual program will use 3 heaps of 13 coins.

  • Player 1 takes 4 coins from heap 2, leaving the heaps with 5, 1 and 5 coins
  • Player 2 choses to take 4 from heap 3, leaving 5, 1, 1
  • Player 1 then takes 1 coin from heap 1 leaving 4, 1, 1. (Player 1 is obviously an idiot…)
  • Player 2 now takes 4 coins from heap 1, leaving 0, 1, 1.
  • This means that Player 1 has to take the last coin from either heap 2 or heap 3, meaning that Player 2 will win as they take the last coin remaining.

Your task is to write an implementation for two human players who share the same computer and keyboard and take turns to play - there is no ‘AI’ in this.

Because of the varying level of programming expertise, there are four levels of implementation - each of which is worth (slightly) more marks than the one before. You can choose which level you attempt.

Levels of Assessment

Because programming experience varies, I have set four possible levels of achievement for this assessment - you can aim for any level you want (though I strongly recommend you solve Level 1 first - in stages, as described in the course - and then build on your solution to solve the higher levels - don't just "jump in" with Level 4).

There is no need to use any features of Java beyond Chapter 6 (you can - provided what you use appears in the course notes at some point - if you want but doing so will not automatically improve your mark - there has to be a sensible reason).

Level 1 - Minimum Acceptably Correct - Assumes all Input is Correct

For this version you do not need to do any checking of input data - you can assume that the users will always enter correct data. That is,

  • You can assume users only ever type in integers where integers are expected
  • You can assume the integers they type will always be > 0 and < number left in the heaps (or the number of heaps, as appropriate), AND that the numbers they enter are squares (1, 4, 9).

It is acceptable that this version crashes (or otherwise doesn’t work properly) if the user does not enter integers, or if they enter integers outside the allowed ranges. The maximum possible mark for this version is 70% (61% excluding exceptional categories).

Level 2 - Some Input is Correct

The second level checks to ensure that the user has entered only integers, BUT it does NOT have to check those integers are correct. That is, it does not need to check that the chosen heap is legal or that there are still coins left in that heap. Nor does it have to check that the number of coins taken is a square. If the user enters a non-integer, then your program should ask the user to re-enter data.  The maximum mark available at this level is 75% (66% excluding exceptional categories). Level 2 is not much more difficult than Level 1 - hence there are not many more marks available.

Level 3 - All Input is correct

The third level ensures that input is ALL correct. That is, that only integers are entered; that the chosen heap is always legal (and has some remaining coins); and that the chosen number of coins is a square. That is, your program should not crash and should correctly play the game - by asking for input to be re-entered if necessary - no matter what the user types. The maximum mark available at this level is 90% (81% excluding exceptional categories). Level 3 is actually quite a bit more tricky to do properly than Level 2 (hence there are more marks for it).

Level 4 - Players can Skip ONE turn

The fourth level modifies the rules of the game slightly. In this level, each player has ONE opportunity to skip a turn. If they do, it's immediately the other player's turn. Attempting to skip a second turn should be rejected. The maximum mark available at this level is 100% (91% excluding exceptional categories). Level 4 is more difficult to do than you think - and it's easy to end up losing style and structure marks when attempting it e.g. by finding you 'need' to use break or continue - you actually don't. The marking rubric is deliberately designed to discourage attempts at Level 4 that are not well thought-out. Only attempt if you are confident.

Marking Criteria

The mark you get is not just based on whether your code works or not.

Your work will be assessed using a marking rubric in Canvas - you can and should read this: it will tell you what you need to do to get marks in each category.

Because there are four lab tasks each worth 2.5% of the module that also contribute to the mark for this assessment, it is actually marked out of 140 - 100 marks for the coursework and 40 for the lab tasks, it will be marked out of 140 (and that mark will be converted to a % when it's uploaded to the University systems).

The categories are:

  1. Compiles - 10/140 of marks are for your code compiling; marks are deducted if, for example, there are compiler warnings.
  2. Function - 35/140 of marks are for your code working: if you reach Level 1 above you will get 5%; if you reach Level 2 you get 10%; if you reach Level 3 you will get 25%; and if you reach Level 4 you get 35%. Remember, you must pass ALL the tests in a level to get the marks for that Level. If you somehow, say, manage to pass the tests for Levels 1, 2 and 4 but NOT (say) 3 - then you solution will be marked as correctly implementing Level 2 (NOT Level 4).
  3. Code Layout and Style - 15/104 of marks are for your programming style. This will be checked using the CheckStyle program, by Autograder. Autograder will check your code with two separate styles - corresponding to the two bracketing styles. Your code must pass ONE of them to get style marks (it's obviously impossible to pass both at the same time).
  4. Code Structure - 20/140 of the marks are for how you structure your program: that is, how you choose to actually solve the programming problem. So good solutions for example will avoid repeating code, or becoming too long. Also what counts as "repeated code" will become stricter at higher levels. This category also rewards solutions that allow the number of coins in each heap to be easily changed.
  5. Identifiers- 10/140 of the marks are for identifier (e.g. variable) names and using final variables (constants). That is, have you chosen sensible and readable names? Have you identified all the sensible choices for constants? (The actual format of names and whether they meet Java programming style rules will be tested automatically by CheckStyle as part of the ‘Code Layout and Style’ mark category).
  6. Comments - 10/140 of the marks will be for sensible (meaningful, well placed and not excessive) commenting.
  7. Lab Tasks - 40/140 of the marks are for lab tasks 1 to 4.

Each of these categories has a number of sub-sections, and the marking rubric has text telling what you need to do to get a mark in each category.  This coursework is worth 15% of CS-110.

What This Means in Practice

Marking criteria are intended to assess ability, and very high marks should indicate very high ability. 61% of the marks will be available for Level 1 solutions that do not reach the top structure category, and 66% for Level 2 solutions that do not reach that category. Remember that a first class mark is 70%.

Level Descriptions

Below are descriptions of what it means to implement each level - what you need to do and what messages you need to output (and how). You need to follow these instructions very carefully. There is no way for your submission to be considered correct if you don't. So, for example, don't put extra messages in; or change the text of the messages - that's guaranteed to fail the tests.

It's actually quite hard to write descriptions like this, and there may be ambiguities. However, you will be judged using Autograder- so treat that as definitive. That is, if you think it doesn't agree with what is said here, you need to follow Autograder.

All games start with 3 heaps each containing 13 coins.

Level 1

At the start of each player's turn the following will be output:

Remaining coins: X, Y, Z
Player A: choose a heap: input here

where X, Y and Z are the number of coins currently in each of the three heaps (remember they will all start at 13), A is either 1 or 2 (for player 1 or player 2) and input here is where the user will enter their chosen heap. Your code should not output 'input here'.

After choosing a heap, the user will be prompted to choose a number of coins:

Now choose a square number of coins: input here

After this, the program should return to print the number of remaining coins (see above) and ask the other player to choose a heap. When the game is over, the output should be:

Player A wins!

where A is either 1 or 2.

Level 2

Level 2 is the same as level 1 except that if the user enters anything other than an integer, the program should print:

Sorry you must enter an integer or skip.

when asked which heap they want to choose, and

Sorry you must enter an integer.

when asked to choose the number of coins they want to take.

At this point, you can ignore 'skip' - that is for Level 4 (it's only present in the message here to keep them consistent for the tests).

After that, it should re-prompt the user for input using exactly the same message as the one where they failed to enter correct data.

Level 3

Level 3 is the same as Level 2 except that it must check that the numbers the user enters obey the following rules:

  • The heap must be between 1 and 3 and must not be empty.
  • The number of coins chosen must be a square; must be positive (> 0); and must be less than or equal to the number of coins remaining in the heap.

If these conditions are not met, it must print the following message:

If the heap choice is not legal:

Sorry, that's not a legal heap choice.

If the coin choice is not legal:

Sorry that's not a legal number of coins for that heap.

Level 4

Do not underestimate how difficult it is to do Level 4 without losing points for code structure. You probably need to read ahead in the notes to do a good job.

Level 4 is the same as Level 3 except that when prompted for a heap choice, you can also enter skip. If you do that, provided you have not already done so in the game, you will skip your turn and the other player will immediately be asked to choose a heap. For example:

Player 1: choose a heap: skip
Player 2: choose a heap:

If you have already used your skip then the program should show the following message:

Sorry you have used your skip.

and ask the player to choose a heap again.

Automatic Testing and Scanners

Because of the way this testing and Scanners work, you need to obey a couple of rules.

  • You should only have one Scanner in your code.
  • You should not create that Scanner in a loop.

So this is wrong:

Scanner in = new Scanner(System.in);
Scanner in2 = new Scanner(System.in)

and so is this:

while(…) {
    Scanner in = new Scanner(System.in);
   …
}

Both of these will, unfortunately, work when you test from the keyboard but fail the automatic testing.

Guidance Notes

  • The biggest mistake you can make is failing to start the work early enough - you need to not only get the code written and compiling, but also working and matching the output of the automatic tests. You need to give yourself time to deal with any hitches, and see me if you need to. You also need to give yourself time to carefully submit your work - uploading the wrong file to Canvas in a panic at the last minute happens at least once every year, and unfortunately there's no way to fix that once the deadline has passed.
  • The second biggest mistake you can make is just to start writing code without thinking about what you are doing. Don’t just jump in and start writing - make a plan!
  • Break the program into parts - there are three steps in this program: player one chooses which heap to take from and takes coins; player two chooses which heap to take from and takes coins; the program decides if the game is over and if so, who has won. Note that the code for the first two parts is nearly exactly the same - take advantage of that. A good solution does not repeat this code (and you can do that without having to use ANY features of Java we have not seen yet.)
  • Start with Level 1 and work up - if you do that and don't manage to complete a higher level you will have something that works that you can submit. If you start at Level 4 and don't get it working you have essentially nothing. The marking scheme penalises you if there code present for a level that does not work - so if you for example, have code that attempts to handle 'skip' but your code only passes Level 3, you will lose code structure marks.
  • Once you have something that works at a particular level, make a backup copy - that way if you don't get a higher-level working, you are not trying to recreate an earlier version at the last minute. And you have a version to submit that does not include not-working code for a higher level (see point above).
  • Write and test in parts - there is no need to try to do everything in one go: write the program in parts so you can test and check each part on it’s own without worrying about the rest of it.
  • Don’t be afraid to write test code - if you’re going to write your program in parts, you need write some extra test code. For example if you are writing the bit that decides if the game is over and who has won, you need to write some code to set the numbers of coins in the heaps to dummy values. Sometimes people shy away from writing this code when they start - thinking the work is ‘wasted’ if it’s not code they are going to submit. But it makes it easier and quicker to solve the problems you face, so it’s not wasted effort - it’s less effort and most code written in industry is probably test code.
  • Don’t be afraid to ask for help - it’s my job to help and guide you (not do it for you though) so please ask if you have problems - there is no 'penalty' for doing this (though not the exceptional performance parts where you need to do things yourself).
  • Don’t be tempted by unfair practice - it’s sometimes tempting to submit someone else’s solution (maybe changed a bit…), or get something off the internet, or ask someone else to do it, or just to ask them for a bit of code to solve a particular problem (or give a bit of code to someone else), or get AI to do it. If you do this you risk serious penalties for breaching academic integrity. Remember we have systems that detect these practices and the minimum standard penalty is 0% for the the WHOLE of CS-110 (not just the coursework). Also the penalties will apply to EVERYONE involved - so even if it's your code that's been submitted by someone else, you will be penalised unless you can convincingly show it was obtained without your knowledge.
  • Read the marking criteria - you have access to the marking rubric on Canvas that tells you what will be assessed, how many marks are for each part, and what you need to do to get a mark in each category. Please pay attention to this.
  • Don’t get carried away - every year I get advanced solutions to coursework that gets a lower mark than some simpler solutions. This is because the advanced solutions focus too much on the ‘advanced’ things and forget the simpler basics (which are in the marking scheme).
  • Remember the marks for style - this is about ensuring your code is readable, and to help it to be maintainable in the future. Nobody will be doing that with your coursework, bit it is likely to form a big part of your future career.
